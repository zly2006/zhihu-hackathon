# 决策数据分层

本项目不是把所有回答硬改写成“答案”，而是把回答保留在原始层，再逐步生成可检索的决策情景。每一层都保留 `content_snapshot.id`，因此结构化结果始终可以回到知乎原文、URL 和 HTML。

## 三层数据

| 层 | 内容 | 用途 |
| --- | --- | --- |
| 原始层 | `content_snapshot` 的问题、回答、来源 URL、HTML、作者字段 | 事实底座，永不删除 |
| 候选层 | 从回答提炼的决策对象、背景、决策、行动、结果、证据摘录和质量状态 | 允许保留不确定案例，供后续检索和复核 |
| 确认层 | 通过证据和一致性校验的候选 | 生成 embedding、合并相似情景、在线召回 |

候选层不应因为一次模型判断失败而丢失。至少保留以下状态：

- `ACCEPT`：证据完整，适合进入确认层；
- `REVIEW`：有决策线索，但作者行动、对象或结果不够确定；
- `REJECT`：当前回答明显是建议、教程、假设或与决策无关。

`REJECT` 也保留原因，方便调整规则后重新处理；它不是从原始库删除数据。

## 单条决策情景

确认层的最小结构保持简单：

```json
{
  "id": "content_snapshot.id",
  "decision_object": "是否转行到互联网行业",
  "context": "做出选择前的处境和约束",
  "decision": "最终选择或正在比较的方向",
  "action": "作者实际采取的行动",
  "outcome": "已观察到的结果；未知时为空",
  "evidence_quote": "回答中的原文证据",
  "confidence": 0.94
}
```

`evidence_quote` 必须能在对应回答中逐字找到（允许空白归一化），否则不能进入确认层。确认层只负责“回答 → 决策情景”，不替作者补写不存在的结果。

## 处理漏斗

以 2026-08-28 的一次本地 4090 运行作为示例：

```text
10,397 条原始回答
        ↓ 模型初判
   726 条决策相关候选
        ↓ 证据/对象/作者行动规则
   288 条严格候选
        ↓ 二次自动复核
   265 条确认情景
```

这个数字表示确认层的规模，不代表数据库只剩 265 条。其余回答仍在原始层，未通过的候选应在候选层以状态和原因保留。若目标是覆盖“正在考虑”或“他人案例”，应将它们标为 `REVIEW`，而不是强行当成已完成的个人决策。

## 检索使用方式

1. 对确认层的 `decision_object + context + decision + action + outcome` 生成 embedding。
2. 用户输入只召回相似的决策对象和处境；原文通过 `id` 回查。
3. 按 `confidence`、证据完整度和相似度排序，确认层优先，`REVIEW` 作为补充。
4. 场景合并和分叉分析在 embedding 召回之后进行，不在采集阶段修改原始回答。

数据库写入和 schema 迁移仍由上游受治理仓库负责；本仓库只读取只读快照并消费确认层结果。
