# Restart Life 主角创建页设计方案

> 文档用途：交给后续 agent 设计或实现主角创建页。
>
> 当前状态：`design-complete / implementation-pending`
>
> 视觉基准：`docs/ui-prototypes/galgame-style-lab/index.html`
>
> 业务入口：`app/life/page.tsx` → `components/life/LifeApp.tsx`

## 1. 页面定位

主角创建页不是普通注册表单，而是玩家进入人生模拟前完成的“18 岁人生档案”。页面负责收集主角公开背景、人格内核、初始目标与天赋，并把合法的 `ProtagonistDraft` 交给现有 NPC 生成流程。

玩家完成本页后进入“三位核心关系确认页”，而不是直接进入第一章。

```text
开始新人生
  ↓
主角创建页 protagonist-creation
  ↓ POST /api/life/npc/generate
生成并确认 3 位核心 NPC npc_setup
  ↓ POST /api/life/create
创建 GameSave v1
  ↓
人生阶段 / 第一章
```

## 2. 设计目标

1. 保留 MVP 已验证的半结构化创建字段和 API 链路。
2. 让玩家在 3–5 分钟内完成创建，不要求写长篇人物小传。
3. 继承当前场景页的暖米白四边框架、都市动画气质和人物头像语言。
4. 让“选择如何影响起点”可见，但不承诺固定结局或给出虚假的最优解。
5. 在提交前形成可读的人物摘要，减少生成 NPC 后才发现设定错误的返工。
6. 知乎授权只用于预填昵称和头像，不根据真实知乎内容推断玩家人生。

## 3. 非目标

- 不在本页生成三位 NPC；这里只发起已有生成接口。
- 不在本页生成 Life Theme、Stage Goal 或第一章剧情。
- 不接入实时 AI 对话式捏人。
- 不把玩家知乎回答、关注、收藏或浏览历史用于人物推断。
- 不在创建阶段直接修改 `LifeStats`、关系值或世界事件。
- 不把头像实时生图放进 V1 核心链路。
- 不修改数据库 schema，不写入 PostgreSQL。

## 4. 方案选择

### 4.1 采用：单页四边“人生档案台”

玩家在一个页面内完成四组信息，左侧显示进度，中间填写档案，右侧实时预览角色，底部统一提交。

优点：

- 与当前已确认场景页结构一致。
- 玩家可以同时看到输入和最终人物摘要。
- 能复用现有 `ProtagonistSetup` 的本地状态和一次性提交方式。
- 不需要新增路由或多页草稿同步。

### 4.2 未采用：多步向导

多步向导能降低单屏密度，但会增加前后切换、草稿恢复和跨步骤校验；也会削弱当前四边框架的整体感。移动端可以使用分段折叠模拟逐步填写，不需要把数据拆成多个页面。

### 4.3 未采用：AI 对话式创建

对话式创建更有叙事感，但会引入模型延迟、结果漂移和隐私误解，也无法保证准确生成 `ProtagonistDraft` 的所有硬字段。本版本不采用。

## 5. 桌面布局

参考尺寸：1440×900；页面沿用当前场景页的四边框架。

```text
┌──────────────────────────────────────────────────────────┐
│ 品牌        序章 · 建立人生档案        创建进度 01 / 02 │ 顶部框架
├────────────┬───────────────────────────────┬─────────────┤
│ 创建进度   │                               │ 角色预览    │
│ 01 基本身份│  人生档案主表单               │ 动画头像    │
│ 02 出身起点│  当前展开一个主要分区         │ 姓名/18岁   │
│ 03 人格内核│                               │ 起始年/城市 │
│ 04 初始天赋│                               │ 标签/价值观 │
│ 05 最终确认│                               │ 天赋概览    │
├────────────┴───────────────────────────────┴─────────────┤
│ 返回首页          草稿已保存       生成三位核心关系 →   │ 底部框架
└──────────────────────────────────────────────────────────┘
```

### 5.1 顶部框架

- 左：产品品牌与 `Restart Life`。
- 中：`序章 · 建立人生档案`，副标题 `18 岁是起点，不是判决`。
- 右：`创建进度 01 / 02`、帮助、返回标题页。
- 不显示存档、角色状态或章节年份；这些尚未建立。

### 5.2 左侧进度栏

五个锚点：基本身份、出身起点、人格内核、初始天赋、最终确认。

- `未开始`：空心圆与浅灰文字。
- `进行中`：香槟金菱形与深棕标题。
- `已完成`：金色勾选。
- `有错误`：低饱和砖红感叹号。
- 点击已开始的锚点滚动到对应分区；不清空字段。
- 桌面宽度不足时可收起为 48–50px 纵向轨道，沿用当前时间线收起逻辑。

### 5.3 中央档案区

中央不是夜景舞台，而是一张暖米白“档案纸”。四个输入分区依次垂直排列，当前分区强调，已完成分区可折叠为摘要。

- 表单底色：`#FBF3E5` 至 `#EAD8BD` 的轻渐变。
- 正文：深棕 `#403326`；辅助文字 `#75685A`。
- 强调：香槟金 `#D6A75E`；错误：低饱和砖红。
- 卡片圆角、描边和阴影继承当前场景页。
- 所有中文字由 HTML 渲染，不写入背景图。

### 5.4 右侧角色预览

- 顶部：当前头像，大尺寸圆角方形；下方可切换预设头像。
- 中部：姓名、性别、18 岁、起始年份、家乡、初始城市、起点方向。
- 下部：性格标签、价值观、长期目标、初始困境和五项天赋条。
- 信息未填写时显示引导文案，不使用“你”“男”“女”等文字代替头像。
- 右栏只预览玩家已经填写的事实，不调用模型补全。

### 5.5 底部框架

- 左：`返回首页`。
- 中：草稿状态，例如 `已保存于本机 · 14:32`。
- 右：主操作 `生成三位核心关系 →`。
- 主操作只有在所有 P0 字段合法、天赋预算正确时可用。
- 提交后按钮进入 `正在构建关系…`，同时显示可读的阶段提示；禁止重复提交。

## 6. 移动端布局

参考尺寸：390×844。

- 顶部保留品牌缩写、页名和完成度。
- 左侧进度栏改为顶部横向五段进度条。
- 中央分区使用手风琴；一次只展开一个，已完成分区显示两行摘要。
- 右侧角色预览改为每个分区顶部的紧凑头像卡，不使用抽屉覆盖输入。
- 底部框架固定，包含返回与主操作；主操作高度至少 48px。
- 键盘弹出时底部框架允许进入文档流，避免遮挡当前输入。
- 标签、选项和加减按钮触控目标至少 44×44px。

## 7. 字段与交互设计

### 7.1 基本身份

| 字段 | UI | 规则 | 映射 |
|---|---|---|---|
| 姓名 | 单行输入 | 必填；去首尾空格；建议最多 12 个中文字符 | `name` |
| 出生年份 | 数字输入 + 起始年提示 | 必填；1950–2026；实时显示 `18 岁起始于 XXXX 年` | `birthYear` |
| 性别 | 三项单选 | 男 / 女 / 其他；不用于限制剧情资格 | `gender` |
| 家乡 | 可搜索输入 + 常用城市建议 | 必填；保存玩家文本 | `hometown` |

### 7.2 出身起点

| 字段 | UI | 规则 | 映射 |
|---|---|---|---|
| 家庭背景 | 预设卡 + 自定义 | 必填；预设只负责快速输入，不直接偷偷修改数值 | `familyBackground` |
| 初始城市 | 可搜索输入 | 必填；允许与家乡相同 | `initialCity` |
| 起点方向 | 预设卡 + 自定义 | 必填；例如学生、程序员、服务业、待业、自由职业 | `initialDirection` |

家庭背景建议预设：

- 拮据但关系紧密
- 普通工薪家庭
- 小有余裕
- 家境优渥但期待较高
- 单亲或重组家庭
- 自定义

预设必须保持描述性，不把家庭背景直接转换成隐藏的现金保底或成功率奖励。真实影响应由后续世界状态和事件结算承担。

### 7.3 人格内核

| 字段 | UI | 规则 | 映射 |
|---|---|---|---|
| 性格标签 | 多选标签 + 自定义 | 3–5 个；禁止重复；每个建议 2–6 字 | `personalityTraits` |
| 价值观 | 多选标签 + 自定义 | 2–4 个；禁止重复 | `values` |
| 长期目标 | 单行或短文本 | 必填；建议不超过 40 字 | `longTermGoal` |
| 初始困境 | 短文本 + 快速建议 | 必填；不想自述时可选“暂时没有明确困境” | `initialDilemma` |

性格建议分组展示，避免把“善良、聪明”等全是正向词堆在一起：

- 行动方式：谨慎、果断、冒险、耐心、好胜。
- 社交方式：外向、内敛、共情、独立、讨好。
- 压力反应：韧性、逃避、固执、反思、求稳。

价值观建议：稳定、家庭、自由、成就、诚实、归属、财富、创造、责任、公平。

### 7.4 初始天赋

保留五项领域定义：洞察、亲和、韧性、学习、运气，对应现有 `Talents`。

推荐 UI 规则：

- 后端值保持 0–100。
- 页面默认每项 50，总预算 250。
- 单项可分配范围 20–80，步长 5。
- 增加一项必须从其他项扣除；不能把五项全部拉满。
- 支持 `均衡`、`社交型`、`学习型`、`坚韧型` 四个预设，预设也必须满足总预算 250。
- 每个天赋提供一句机制说明，不承诺“选高就一定成功”。

建议显示：10 段式进度条、减号、数值、加号和剩余预算。不要直接复用旧版 1–7 点圆点控件的数值。

#### 天赋数值风险

现有新版 `Talents` 是 0–100，但 `decision-resolver.ts` 中的保护公式直接按 `0.8 / 0.7 / 0.35` 相乘。默认 50/50/50 会产生 92.5 点保护并经常把风险压到最低值。这与旧版 1–7 天赋尺度不一致。

后续实现前必须单独确认并测试数值归一化；创建页不得通过把 UI 改回 1–7 来掩盖这个问题。推荐由结算层明确把 0–100 天赋转换为合理的风险修正区间，例如先除以 10，再参与公式。最终系数需要以极端状态和普通状态测试确定。

## 8. 头像设计

### 8.1 P0 方案

- 提供 6–8 个预生成的成年都市动画头像，覆盖不同性别表达和气质。
- 头像是视觉身份，不改变性格、数值或剧情资格。
- 已授权知乎账号时，可以在玩家明确选择后使用知乎头像作为默认项。
- 未授权或不使用知乎头像时，必须显示真实的预设人物头像，不用姓名首字占位。
- 不在本页实时调用图像模型，避免创建链路被生图延迟阻断。

### 8.2 数据建议

当前 `Character` 没有头像字段。后续实现若需要在所有页面稳定复用头像，建议新增可选视觉字段，而不是根据姓名或性别临时猜测：

```ts
type CharacterVisualIdentity = {
  avatarSource: "preset" | "zhihu";
  avatarId?: string;
  avatarUrl?: string;
};
```

- `preset` 使用项目内稳定 `avatarId`。
- `zhihu` 保存公开头像 URL，并继续通过现有 `/api/avatar?url=` 代理显示。
- 该字段必须保持可选，避免破坏旧 `GameSave v1` 读取。
- 不把头像内容交给模型反推人格、收入、家庭或关系。

## 9. 页面状态

| 状态 | 表现 | 可执行操作 |
|---|---|---|
| `default` | 默认值和空字段 | 填写、选择头像、返回 |
| `editing` | 当前分区高亮，预览实时更新 | 修改、切换分区 |
| `incomplete` | 左栏标出未完成项，底部按钮禁用 | 跳转到首个缺失字段 |
| `invalid` | 字段级错误；保留所有已填内容 | 修正、重新提交 |
| `draft-restored` | 显示“已恢复本机草稿” | 继续或清空草稿 |
| `submitting` | 按钮锁定，显示 NPC 生成进度 | 可取消仅在请求尚未完成时提供 |
| `submit-error` | 顶部错误摘要 + 字段内容不丢失 | 重试或返回编辑 |
| `mobile` | 分区手风琴和紧凑预览 | 顺序填写、固定主操作 |

## 10. 校验与错误文案

### 10.1 客户端校验

- 姓名不能为空。
- 出生年份必须在 API 接受的 1950–2026 范围。
- 家乡、家庭背景、初始城市和起点方向不能为空。
- 性格标签必须 3–5 个。
- 价值观必须 2–4 个。
- 长期目标和初始困境必须有有效文本。
- 天赋每项 20–80，合计必须等于 250。
- 头像必须有稳定选择。

### 10.2 服务端错误

- `400 主角信息不完整`：定位到基本身份，并保留草稿。
- `400 出生年份需在 1950 到 2026 之间`：聚焦出生年份。
- NPC 生成失败：保留全部表单和头像选择，底部显示重试，不自动重复扣请求。
- 网络断开：提示“档案已保存在本机，联网后可重新生成核心关系”。
- 页面离开：有未提交修改时提示；已自动保存则允许直接离开。

## 11. 草稿与隐私

- 建议使用独立本地键：`restart-life-protagonist-draft-v1`。
- 只存储本页显式输入和头像选择，不存储模型推断。
- 完成 `/api/life/create` 并写入正式 `GameSave` 后清理创建草稿。
- “清空草稿”是破坏性操作，需要二次确认。
- 不把主角创建信息写入当前只读内容数据库。

## 13. 推荐组件边界（供实现 agent 参考）

设计建议拆分，不要求本轮创建代码：

```text
components/life/protagonist-creation/
  ProtagonistCreationPage.tsx    页面状态、提交、草稿恢复
  CreationProgressRail.tsx      左侧分区进度
  IdentitySection.tsx           基本身份
  OriginSection.tsx             出身起点
  PersonalitySection.tsx        标签、价值观、目标和困境
  TalentAllocator.tsx           0–100 天赋预算
  AvatarPicker.tsx              预设 / 知乎头像
  ProtagonistPreview.tsx        右侧实时摘要
  CreationActionBar.tsx         返回、草稿和提交
  protagonist-creation.css      页面局部样式
```

页面组件向 `LifeApp` 暴露的接口保持简单：

```ts
type ProtagonistCreationPageProps = {
  initialDraft?: Partial<ProtagonistDraft>;
  accountProfile?: {
    name: string | null;
    avatarUrl: string | null;
  } | null;
  loading: boolean;
  error: string;
  onBack: () => void;
  onSubmit: (draft: ProtagonistDraft) => void;
};
```

头像视觉字段如果尚未进入 `ProtagonistDraft`，可由页面以单独参数提交给上层；不要临时塞进 `familyBackground` 或其他文本字段。

## 14. 可访问性与输入要求

- 所有输入有真实 `<label>`；错误通过 `aria-describedby` 关联。
- 左侧进度使用列表或步骤语义，不伪装成 tab。
- 头像选择使用单选组，提供可读名称。
- 天赋加减按钮提供“提高洞察”“降低洞察”等标签。
- 颜色不能作为完成、错误或选中的唯一表达。
- 支持键盘完整完成流程。
- 遵守 `prefers-reduced-motion`；分区折叠 160–220ms。
- 手机触控目标至少 44px，正文最低 14px。

## 15. 验收标准

### 15.1 视觉

- [ ] 与已确认场景页属于同一套暖米白四边 UI。
- [ ] 3 秒内能识别页面目的和主操作。

## 16. 后续实现前必须确认的技术问题

以下不是设计占位，而是仓库审计得到的明确风险：

1. **天赋尺度不一致**：新版 0–100 天赋与结算公式的系数需要先做数值归一化测试。
2. **头像未进入 Character**：需要决定采用可选视觉字段，还是在独立 UI 元数据中持久化；禁止按姓名临时映射。
3. **新版 LifeApp 未读取知乎状态**：如需昵称/头像预填，应复用 `/api/auth/status`，不能复制旧 OAuth 实现。
4. **现有服务端校验偏少**：API 目前只强校验姓名和出生年份；实现时应让客户端与服务端共享其余 P0 字段校验，避免只靠按钮禁用。
5. **LifeApp 体积增长**：创建页内部草稿、校验、分区与头像状态应留在页面组件，不继续堆进 `LifeApp.tsx`。

这些问题需要实现 agent 在写 UI 前形成测试和明确决策，但不阻止本设计作为页面视觉与交互基准。
